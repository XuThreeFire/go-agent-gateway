# 08 可靠性、成本与测试

目标：用行为证据判断系统能保证什么。前置：读懂前面七章。

## 先运行自动化用例

```bash
make test vet web-test web-build
```

没有配置测试数据库时，MySQL 集成用例会显式跳过；单元测试通过不能证明事务和完整 HTTP 链路可靠。按照[贡献指南](../../CONTRIBUTING.md)配置独立测试库，再运行 `make test-integration`。

## 本项目的保障与边界

| 能力 | 当前行为 | 边界 |
| --- | --- | --- |
| 终态竞争 | CAS 条件更新，终态不回退 | 数据库不可用时无法承诺成功收尾 |
| 批量落库 | 每 Run 串行写入，失败批次保留，幂等重试 | 批量 INSERT 减少往返，不减少事件行数 |
| 实时与补发 | 注册订阅时保存未落库快照，按 seq 去重 | 已看到但尚未落库的尾批可能在强制退出时丢失 |
| 正常关闭 | 等执行器收尾后刷新事件尾批 | 超过关闭期限或 SIGKILL 仍可能中断 |
| 上游重试 | 仅 429，且限未开始输出的请求 | 不重试已输出内容，避免重复文本与工具请求 |
| 日配额 | 客户端与全局日用量在每模型步骤与 Run/Step 同事务累计 | 供应商 usage 可能缺失；并发请求可能同时通过检查 |
| 单 Run 预算 | 每步前检查已知 token，用最大输出与步数兜底 | 无法承诺精确费用上限，单次调用可能超过剩余额度 |

不把供应商未返回的用量记为“实际消耗 0”的计费保证。模拟模式的数字明确只是演示。

## 故障用例阅读顺序

`hub/reliability_test.go` 验证写失败和落库中的订阅；`llm/client_test.go` 验证流截断；`api/security_test.go` 验证身份与归属；`store/integration_test.go` 验证真实 MySQL 事务和唯一索引；`api/integration_test.go` 验证 HTTP 到工具执行再到回放。

练习：在本地测试替身中注入一次事件写入失败，说明为什么“把批次从 pending 移出后只打日志”会让补发丢内容。完成标准是正式回归用例能稳定复现并验证恢复，不依靠手工观察几次。

## 全局每日 token 软配额

`quota.daily_tokens_global` 未配置时默认 500 万，显式 `0` 表示不限，正数使用该值；负数拒绝启动。全局闸先检查，再检查当前签名身份的客户端配额，两种读取失败都会阻止继续调用模型。

全局计数使用 `usage_counter` 的 `global_day` 维度和 `all:YYYYMMDD` 键，客户端继续使用 `client_day`。不新增表或外键，也不需要结构迁移。Step、Run、客户端与全局用量在同一事务提交，任一写入失败全部回滚。日期取步骤实际落库时间并统一 UTC。

升级前已经发生的历史消耗不会自动回填全局桶，计数从新版本提交的模型步骤开始。并发请求仍可能同时通过检查，供应商没有返回 usage 的调用仍可能漏记，因此它是软配额，不能保证精确账单上限。

无需 MySQL 的事务回归见 `store/run_test.go`（SQLMock）；它验证四类记录的一起提交与失败回滚，但不能替代真实 MySQL 集成测试。缓存观测见[模型运行时参考](../reference/model-runtime.md)。
